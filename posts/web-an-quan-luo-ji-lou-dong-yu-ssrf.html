Web 安全：逻辑漏洞与 SSRF

Web 安全 2026-08-28 4595 字 约 12 分钟

来源：课程实验《逻辑漏洞与SSRF攻击》（DVWA 平台 + Burp Suite，2025-2026 第二学期）
定位：业务逻辑漏洞是护网/众测的拿分大头，越权、SSRF、弱会话是面试的高频考题
实战场景：登录/注册/改密/找回密码等业务功能；一切让服务器请求 URL 的功能（图片代理、导入、网页截图）

一、原理概述

一句话原理：Web 安全的另一大类漏洞不是"代码写得烂"（如注入），而是业务逻辑设计有缺陷——校验只做了一半、信任了不该信任的假设、流程可被预测。

与注入类漏洞的本质区别：注入是"输入没过滤"；逻辑漏洞是"该想没想到"。比如：
- 前端把管理按钮藏起来，但后端接口照样能访问——"隐藏 ≠ 鉴权"
- 验证码校验只做在前端/第一步，第二步直接跳过——"流程只走了一半"
- 会话 ID 用自增数字——"标识符可预测，伪造身份"

共同点：攻击者不做任何"技术暴力"，只是顺着业务规则的漏洞走，所以常规 WAF、代码扫描器很难发现，全靠人肉手工测试。

二、越权攻击（Authorisation Bypass / IDOR）

原理

服务器只在"界面层"做了限制（非管理员看不到管理入口），但后端接口本身没有鉴权——任何持有合法会话的人直接请求接口 URL，就能执行管理操作。常见的资源型越权（IDOR）则是：查询接口用 id 参数定位资源（如用户信息），却不校验这个 id 是不是自己的，把 id 改成别人的就能读到/改到别人的数据。

实操方法论（实验提炼）

  1. 用普通账号登录，访问越权目标 URL —— Low 级别甚至给了一个隐藏的管理页面 URL，直接访问即可进入并修改他人数据
  2. 观察接口：打开开发者工具看页面发起的 AJAX 请求，找到 change_user_details.php、get_user_data.php 这类未在界面上暴露的接口——前端没界面 ≠ 后端没接口
  3. 直接调接口：用 curl 带上自己的会话 Cookie 调接口，改 JSON 里的 id 字段：
curl 'http://192.168.164.130/DVWA/vulnerabilities/authbypass/change_user_details.php' \
  -H 'Content-Type: application/json' \
  -H 'Cookie: PHPSESSID=9c68eab46b52f412b7eb3e1e6ee70cdb; security=medium' \
  --data-raw '{"id":5,"first_name":"Bob_New_New","surname":"Smith_New_New"}'

返回 {"result":"ok"} 即修改成功；get_user_data.php 则可拉出全部用户数据。

为什么会有这个洞（面试说清）

授权（Authorization）校验缺位——接口只验证了"你登录了吗"（认证 Authentication），没验证"你有权做这件事吗"（授权）。水平越权 = 只能操作同级别人的数据（改 id）；垂直越权 = 普通用户操作管理员功能（Low 的隐藏管理页）。

三、Insecure CAPTCHA（不安全的验证码）

原理

验证码用来拦截自动化攻击，但实现时只在前端显示、后端校验逻辑有洞（可跳过、可预测、硬编码）。DVWA 改密流程分两步：第一步输验证码，第二步输新密码——后端却没有真正校验验证码。

各难度绕过

难度 后端逻辑 绕过
Low 两步都只是前端页面 抓包把两步请求合并/改参直接提交即可完成改密
Medium 加了 if(!$_POST['passed_captcha']) BP 抓包给请求体添加 passed_captcha=true 即通过——只判断"参数在不在"，不判断"值对不对"
High 校验：g-recaptcha-response == 'hidd3n_valu3' 且 User-Agent == 'reCAPTCHA' 抓包改两个地方：UA 改成 reCAPTCHA + 请求体加 &g-recaptcha-response=hidd3n_valu3 —— 密钥/判断条件硬编码在源码里，等于白送

方法论要点

  • 验证码攻击三步：界面看流程 → 抓包拆步骤 → 逐请求观察"哪一步真的校验了"
  • 凡是"验证码结果藏在响应、页面、源码里"或"判断条件是固定字符串"的实现，都可直接构造绕过
  • 终极信任链：验证码校验必须发生在服务端的业务处理请求上，且结果不可预测、一次性

四、Open HTTP Redirect（开放重定向）

原理

后端把用户可控的 redirect 参数直接用作跳转目标（header("Location: " . $_GET['redirect'])），不校验目标是否合法。攻击者制造"合法域名上的链接，跳转到钓鱼站"——用户信任域名，被骗走了身份。

各难度绕过（重点记忆）

难度 校验逻辑 绕过 Payload
Low 无校验 ?redirect=https://钓鱼站
Medium 拒绝包含 http:// 或 https:// 的目标（报 500 "Absolute URLs not allowed"） ?redirect=//钓鱼站 —— 协议相对 URL：以 // 开头时浏览器自动按当前页面的协议（http/https）补齐，成功跳转
High 目标必须包含子串 info.php ?redirect=https://钓鱼站?a=info.php —— 把 info.php 塞进一个无害的查询参数里，满足子串判断又不影响跳转

危害与进阶

  • 钓鱼：配合短链接包装，点击"官方链接"进钓鱼站；OAuth/SSO 场景下 redirect_uri 可控可窃取授权码/token
  • 方法论：发现跳转参数 → 测试过滤规则（字符串黑名单还是白名单）→ 读绕过滤则 → 包装投放

五、SSRF（服务端请求伪造）

原理

一句话：某些功能需要"服务器代替用户去请求一个 URL"（图片代理、网页转码、URL 检测），而目标 URL 由用户控制且未过滤——服务器变成了攻击者的跳板，把攻击流量伪装成"服务器发出的合法流量"。

危害分级（面试要背）：
1. 读本地文件：file:// 协议 → 读服务器任意文件（file:///etc/passwd、代码源码）
2. 内网探测：http://192.168.x.x:port → 用响应差异（超时/报错/内容）当扫描器，摸清内网拓扑和存活主机
3. 攻击内网服务：Redis 未授权、Memcached、内部管理后台——利用"内网互信"打穿隔离
4. 云环境打元数据：http://169.254.169.254/latest/meta-data/ 偷云服务器临时凭证（阿里云/aws 经典技）

实验中的两种触发函数

// 方式一：curl 类（实验 URL 形如 url=http://127.0.0.1/ssrf/info1.php）
// 方式二：file_get_contents()（实验 URL 形如 file=http://127.0.0.1/ssrf/info2.php）

file_get_contents() 是 PHP 内置读内容函数——它既能读本地文件也能发 HTTP 请求，无过滤时：php:// 伪协议读源码、file:// 读系统文件、http:///dict:// 探测内网端口。

实操方法论（四步）

  1. 找发起请求的参数：URL 里有 url=、file=、img=、fetch=、redirect= 且页面内容受该参数影响
  2. 先测本地：file:///etc/passwd 能读 → 直接读源码（php://filter）找更多信息
  3. 再测内网：http://127.0.0.1:port → 用响应差异探测本机、http://内网IP段 探测内网
  4. 最后利用：dict 协议扫端口、打 Redis/数据库等内网应用、云上偷元数据

六、Weak Session IDs（弱会话标识）

原理

会话 ID（Cookie）的作用是"告诉服务器我是谁"，如果 ID 可预测，攻击者就能算出/猜出别人的会话，直接冒充。实验三级别展示了三种"可预测性"：

级别 生成规则 破解
Low 自增数字（1、2、3...） 观察规律，把 dvwaSession=2 改成 3 即可成为下一个用户的会话
Medium 基于当前时间戳 抓包看值 → 时间戳转换工具确认格式 → 自己生成"当前时间"的合法值伪造
High md5(自增序号) 拿到的值 MD5 解密 → +1 → 再 MD5 加密 → 预测下一个会话

核心思想：会话标识必须是高熵随机数（足够长的真随机），任何"可枚举、可推算、基于时间的规律"都是漏洞。这类漏洞配合会话固定（Session Fixation，服务端不更换登录后的 session ID）危害翻倍。

七、防御（面试必答）

漏洞 防御
越权 每次请求做授权校验（对象级权限检查）；接口与 UI 一视同仁；资源 ID 用不可枚举的 UUID 并校验归属
CAPTCHA 验证码校验必须在服务端业务请求上、结果一次性随机；硬编码判断条件禁止；用正规 reCAPTCHA 服务端验证
开放重定向 跳转目标白名单校验（只允许站内路径/固定域名集合）；禁止用户参数直接进 Location
SSRF URL 白名单/协议白名单（只允许 http/https）；解析后校验目标 IP 非内网/非回环/DNS rebinding 防护；出网流量经代理并审计；禁用 file/dict/gopher 伪协议
弱会话 session ID 用 CSPRNG 生成、长度足够；登录后更换 session ID（防固定）；HttpOnly + Secure 标志

八、面试速答卡

  • 逻辑漏洞和注入的区别：注入是输入没过滤；逻辑漏洞是业务设计缺校验/流程可预测，工具难扫全靠人测
  • 水平/垂直越权：平级改别人数据（改 id） vs 普通用户干管理员的事
  • 越权为什么测接口：前端藏了 UI 不等于后端鉴了权，接口直接可调
  • CAPTCHA 绕过套路：抓包拆流程找"没真正校验"的那步，或利用硬编码的判断条件
  • 开放重定向 Medium 怎么绕：协议相对 URL //域名，浏览器自动补协议
  • SSRF 危害分级：读文件 → 内网探测 → 打内网应用 → 云元数据窃取
  • SSRF 常见参数名：url、file、img、fetch、redirect
  • 弱会话的根本问题：ID 可预测（自增/时间戳/简单哈希），要用高熵随机数
