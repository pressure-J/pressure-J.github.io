二、Windows 单机应急响应（本机立刻能跑，最贴合现有笔记）

1. SigmaHQ/sigma ★11.3k —— 整个蓝队的「标准库」

不是工具，是规则的通用格式。所有主流工具（Hayabusa、Chainsaw、Splunk、Elastic、Sentinel）都能吃 Sigma 规则，所以它同时是规则仓库 + 语法标准。

规则目录按 rules/windows/process_creation/、rules/windows/builtin/ 这类结构分，每条 yml 结构固定：

title: New User Created Via Net.EXE
id: cd219ff3-fa99-45d4-8380-a7d15116c6dc
status: test            # stable/test/experimental/deprecated —— 决定误报率
description: Identifies the creation of local users via the net.exe command.
references:
    - https://eqllib.readthedocs.io/...
author: Endgame, JHasenbusch
date: 2018-10-30
modified: 2023-02-21
tags:
    - attack.persistence
    - attack.t1136.001       # ATT&CK 编号，工具靠它做战术归类
logsource:
    category: process_creation
    product: windows
detection:
    selection_img:
        - Image|endswith:
              - '\net.exe'
              - '\net1.exe'
        - OriginalFileName:
              - 'net.exe'
              - 'net1.exe'
    selection_cli:
        CommandLine|contains|all:
            - 'user'
            - 'add'
    condition: all of selection_*      # 布尔表达式，可选 1 of / all of them
falsepositives:
    - Legitimate user creation.
level: medium

必须记住的三个字段：

  • logsource —— 决定这条规则扫哪个日志源。Sigma 原文用 service: security 这种抽象写法，Hayabusa 会把它去抽象化成具体的 Channel + EventID（因为它要按 channel 过滤提速）
  • detection —— 修饰符语法是精华：contains startswith endswith all re base64offset windash（把 - 和 / 都兼容，防攻击者换参数前缀）
  • status + level —— 误报率的两把尺子。stable + high 几乎不误报，experimental + low 满屏噪音

为什么值得投入：读规则 = 学检测思路；写规则 = 把 ATT&CK 战术落成可执行判断；提 PR = GitHub 上有可查的 commit 记录。对求职来说这是可验证的能力凭证，比证书硬。

实操入口：git clone --depth 1 https://github.com/SigmaHQ/sigma，然后随便挑一条规则，用你手上的日志手动验证它能不能命中。这一步跨过去，才算真会检测工程。

2. Yamato-Security/hayabusa ★3.4k —— EVTX 快速取证时间线（第一上手工具）

Rust 写的多线程 Windows 事件日志分析器，号称唯一完整支持 Sigma 的工具（含 v2 关联规则）。输入一堆 .evtx 或整个 C:\Windows\System32\winevt\Logs，输出一条带告警等级的时间线（CSV / JSON / JSONL）。

为什么放第一位：单文件 exe，下载解压即用，不用装 Python、不用配环境，是「0 成本拿到第一条攻击时间线」的最短路径。

核心命令是 dfir-timeline（新版本默认带扫描向导，问你要用哪套规则；想按老方式直接指定参数就加 -w / --no-wizard）：

# 扫本机实时日志（最常用）
hayabusa.exe dfir-timeline -l

# 扫一个装满 .evtx 的目录
hayabusa.exe dfir-timeline -d C:\cases\host01\evtx\ -o timeline.csv

# 只保留 high + critical，排除低质量规则
hayabusa.exe dfir-timeline -d .\evtx\ -w --min-level high `
    --exclude-status deprecated,unsupported,experimental

# 输出 JSONL 给 Elastic 吃
hayabusa.exe dfir-timeline -d .\evtx\ -t jsonl -o out.jsonl

# 更新规则库（hayabusa-rules 仓库）
hayabusa.exe update-rules

规则集档位（记住这三档就够）：

档位 条件 等价参数 适用
Core status ∈ {test, stable} 且 level ∈ {high, critical} --exclude-status deprecated,unsupported,experimental --min-level high 生产环境、初筛，误报极低
Core+ status ∈ {test, stable} 且 level ≥ medium --min-level medium 需要额外调优
Core++ status 含 experimental 且 level ≥ medium --exclude-status deprecated,unsupported --min-level medium 抢新威胁，误报高

外加两类标签规则：detection.emerging_threats（针对当下热点威胁，会随时间失效）、detection.threat_hunting（能挖未知活动，但误报多）。传统模式默认都开，向导里可以关。

其它好用的分析子命令（不止 dfir-timeline）：

命令 用途
logon-summary 登录事件汇总（谁在什么时候从哪登录，肉眼找异常最快）
eid-metrics 按 EventID 统计数量和占比（先看分布再决定看什么）
computer-metrics 按主机名统计事件数（多机取证时定位重点）
search 关键词/正则搜索全部事件
pivot-keywords-list 提取可疑关键词（用户名、主机名、路径），用来横向检索
extract-base64 提取并解码事件里的 base64（抓混淆命令）
config-critical-systems 找出域控、文件服务器等关键系统
level-tuning 自定义调整告警等级（降误报）

性能机制值得注意：v2.16.0 起有 Channel 过滤 —— 先读每个 evtx 第一条记录的 Channel，只加载匹配的规则，也跳过无关的 evtx。基准测试里规则侧提速 20%~10 倍，evtx 侧 10%~60%。副作用：如果 evtx 是被人工合并过（一个文件多 channel），得加 -a / --scan-all-evtx-files 关掉过滤；只有两条规则没定义 Channel（Possible Hidden Shellcode、Mimikatz Use），要扫全部文件得加 -A / --enable-all-rules。

3. WithSecureLabs/chainsaw ★3.7k —— 另一个 Rust 快枪 + 自带取证能力

定位和 Hayabusa 重叠，差别在于：Chainsaw 更偏「规则调试 + 快速搜索」，它的 search 子命令能像 grep 一样直接在 evtx 上做字段查询，查东西比 Hayabusa 顺手。

# hunt：用 Sigma 规则跑一批 evtx（必须给 mapping，告诉它 Sigma 字段怎么映射到 evtx 字段）
./chainsaw hunt evtx_attack_samples/ -s sigma/ --mapping mappings/sigma-event-logs-all.yml

# 加上自定义规则、导出 CSV
./chainsaw hunt evtx/ -s sigma/ --mapping mappings/sigma-event-logs-all.yml -r rules/ --csv --output results

# 只看 critical
./chainsaw hunt -r rules/ evtx/ -s sigma/rules --mapping mappings/sigma-event-logs-all.yml --level critical

# 限定时间窗（做「攻击发生在哪个时间点」的收窄）
./chainsaw hunt evtx/ -s sigma/ --mapping mappings/sigma-event-logs-all.yml `
    --from "2019-03-17T19:09:39" --to "2019-03-17T19:09:50" --json

# search：不写规则直接查。关键词 / 字段条件 / 正则三态
./chainsaw search mimikatz -i evtx_attack_samples/
./chainsaw search -t 'Event.System.EventID: =4104' evtx_attack_samples/
./chainsaw search -e "DC[0-9].insecurebank.local" evtx_attack_samples --json

# dump：把注册表 hive、ESE 数据库、MFT 等转成可读格式
./chainsaw dump ./SOFTWARE.hve --json --output ./output.json

Hayabusa vs Chainsaw 怎么选：初筛和出报告用 Hayabusa（时间线最规整、有 level 分档、有汇总命令）；定位具体事件、查可疑字符串、调试自己写的规则用 Chainsaw。两个都跑一遍同一批日志，对比命中差异 —— 差异往往就是规则边界和误报，这是最快的检测工程训练。

4. wagga40/Zircolite ★863 —— 跨平台的 Sigma 离线扫描器

Python 写的，Windows / Linux / macOS 都能跑，支持 EVTX、JSON、Auditd、Sysmon for Linux、XML、SQLite 多种输入，还带 Web UI（zircolite_web.py），把告警结果可视化。适合：

  • 手上只有 Linux（比如 Kali 里分析拷出来的 evtx）
  • 要给非技术人员看结果（Web UI 直接出图）
  • 需要审自己的 Sigma 规则（它有 --package 之类做规则包）

5. 日志采集：Sysmon 配置才是第一道坎

装了 Sysmon 不等于有可用日志 —— 配置文件决定你采到什么、噪音多大。

  • olafhartong/sysmon-modular ★3.2k —— 模块化配置，按 ATT&CK 战术拆成一堆小 xml，按需组合，改起来清晰，最适合自己维护
  • SwiftonSecurity/sysmon-config ★5.7k —— 老牌单体配置，覆盖面广，改起来费劲
# 装 Sysmon 并套配置（modular 需要先合并，或用其提供的合并脚本）
sysmon64.exe -accepteula -i sysmonconfig.xml
sysmon64.exe -c sysmonconfig.xml     # 更新配置

应急响应里常见的坑：客户机器上根本没装 Sysmon，那就只剩 Security/System/Application 三本日志 —— 这时候 4688（进程创建）默认不记录命令行，得靠 ProcessCreationIncludeCmdLine_Enabled 审计策略，而且是事后没法补。所以「采日志」这一步的结论是：先查有没有，再看采集了什么。

三、搭实验环境（虚拟机 / Docker）

6. Velocidex/velociraptor ★4.4k —— 单机自建 EDR，最省事的选择

agent + server 架构，客户端跑 VQL（它自己的查询语言）采集端点数据。蓝队最看重的两个能力：

  1. 全量离线采集：一条 artifact（如 Windows.KapeFiles.Targets）就能把注册表、事件日志、浏览器数据、$MFT 全部打包拉回，不需要人守着
  2. 大规模狩猎：一次下发 VQL 到上千台，回答「哪些机器上有这个 IOC」

比 Wazuh 轻得多，单机也能装，是把「远程取证」从理论变成可操作的最低门槛工具。

7. wazuh/wazuh ★17.3k —— 开源 SIEM + XDR

HIDS（主机入侵检测）、FIM（文件完整性监控）、漏洞检测、日志集中、合规检查全都有。Docker 一键部署（wazuh-docker 仓库），装完就有一个能看告警的 Web 控制台。

代价是重：agent + manager + indexer + dashboard 四件套，资源吃得凶。适合「我要一个能演示的 SOC 面板」的场景。

8. Security-Onion-Solutions/securityonion ★4.9k —— 一体化 SOC 发行版

不是一堆软件的集合，是打磨好的发行版：集成了 Zeek、Suricata、Stenographer、Elastic、Sigma、Strelka 等，装完就是个完整 NSM 平台。适合从头体验「真正的 SOC 长什么样」，但需要独立机器 + 双网卡，别在 16GB 主力机上硬装，用 VMware 单开一台。

9. 网络侧三件套

项目 星 定位
zeek/zeek 8.1k 把流量解析成结构化日志（conn/http/dns/ssl…），是「协议级事实来源」
OISF/suricata 6.7k 签名式 IDS/IPS，靠规则抓已知攻击

在 CTF 流量题里其实已经用过它们的思路：Zeek 日志看「说了什么」，Suricata 告警看「像什么攻击」，Arkime 看「原始字节是什么」。

  • activecm/rita ★661 —— 吃 Zeek 日志，做信标检测和横向移动评分（长连接周期性、DNS 隧道、异常数据量）。做「隐蔽 C2 排查」时很有用
  • idaholab/Malcolm ★490 —— 纯 Docker 把 Zeek + Suricata + Arkime + OpenSearch 打包，比 Security Onion 更适合本地实验，一条 docker compose up 起全套

五、两周上手路线（能落成简历的版本）

第 1 步：打通「日志 → 时间线」（1~2 天）

  1. 装 Sysmon + olafhartong/sysmon-modular 合并出的配置
  2. 随便干点可疑事制造日志（net user hacker /add、whoami、certutil -urlcache）
  3. hayabusa.exe dfir-timeline -l 扫本机 → 看到自己的操作被 high/medium 规则命中

验收：时间线里能对上你自己那几条命令的 EventID、规则名、ATT&CK 编号。

第 2 步：规则验证 + 写规则（3~5 天）

  1. 用 EVTX-ATTACK-SAMPLES 的样本跑 Hayabusa 和 Chainsaw，对比两边命中差异
  2. 挑一个差异项，打开对应 Sigma 规则，看清是哪个字段/修饰符导致的
  3. 找一个自己演练里没被检测到的行为，写一条 Sigma 规则，用样本日志验证能命中
  4. 提 PR 到 SigmaHQ/sigma（先看 CONTRIBUTING，规则要过 lint）

验收：手上有 1 条能跑通、能过 lint、能解释为什么这样写的规则。

第 3 步：完整单机排查记录（1 周）

  1. Velociraptor 采本机全量数据（或手工打包 C:\Windows\System32\winevt\Logs）
  2. Hayabusa 出时间线 + logon-summary 看登录 → 定异常时间窗
  3. Chainsaw search 在该时间窗内定位具体命令/进程
  4. Plaso / EvtxECmd 补充文件系统时间线
  5. 写成一份完整的应急报告（现象 → 证据 → 时间线 → 结论 → 处置建议）

验收：报告里每个结论都能指回具体 EventID + 时间 + 主机。

六、踩坑记录（边用边补）

  • Hayabusa / Chainsaw 都是 Rust 单文件，优先下 release 压缩包，别自己编译
  • Chainsaw 的 hunt 必须给 --mapping，否则字段对不上，规则全部空转
  • Hayabusa 的 Channel 过滤会让「人工合并过的 evtx」漏扫 → 用 -a 关掉；要扫全部规则用 -A
  • Sigma 规则不要原样搬进 SIEM：logsource 是抽象的，得映射到实际索引/字段（Sigma 官方有 pySigma + backend 做转换）
  • pivot-keywords-list 输出的关键词拿去横向检索时，先用 logon-summary 确认哪些主机真被登过，不然检索面爆炸
  • 星数 ≠ 适用性：osquery（★23.6k）和 falco（★9.5k）星都高，但一个偏 Linux 端点查询、一个偏容器运行时安全，普通 Windows 应急用不上
