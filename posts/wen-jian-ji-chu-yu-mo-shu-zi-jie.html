文件基础与魔术字节

基础 2026-09-22 7128 字 约 19 分钟
baseknownmisc

一、什么是文件

文件是计算机里存储数据的基本单位,本质就是磁盘上一段带名字的字节序列。

  • 内容:一堆字节(0/1),用十六进制看最直观。
  • 元数据:文件名、大小、修改时间、权限等,存在文件系统里。
  • 文件系统(如 NTFS)负责把这些字节组织成"文件",否则磁盘只是一大坨原始空间。

文件与内存的区别

文件 内存
存放 磁盘(持久) RAM(断电丢失)
速度 慢 快
目的 长期保存 程序运行时临时用

文件本质上是一个"流":程序读文件就是从头到尾顺序读字节(或随机跳位置读),读到 EOF(文件尾)结束。所以 Python 里 open() 后能 .read()、.seek()。

二、文件类型由"魔数"决定,不是扩展名

扩展名(.txt / .png / .exe)只是给人和系统看的标签,真正决定类型的是文件开头的几个字节,叫魔数(Magic Bytes / Magic Number)。

CTF 里"扩展名骗人、按魔数判类型"就是这个原因。

为什么同类型魔数相同? 因为每个格式都有一份官方规范(specification),明确规定了"本格式前 N 字节必须是 XXX"。写文件的程序和读文件的程序都遵守同一份规范,所以头必然相同——这是人为约定,和网络协议同一种精神。

魔数怎么选出来的

  1. 尽量独特、不易撞车:ZIP 的 50 4B 是 PK,取自作者 Phillip Katz 的名字缩写。
  2. 有时故意加入容错设计:PNG 的头 89 50 4E 47 0D 0A 1A 0A 里,0x89 检测 7-bit 通道丢高位、0D 0A 检测 CR/LF 被转换、1A 是 DOS 的 EOF 字符——一个头塞了好几种容错机制。

注意:魔数不一定在开头
- TAR:在偏移 257 处才有 ustar
- MP4:在偏移 4 处是 ftyp(前 4 字节是长度)
- 所以"只看前 4 字节"是简化说法,严格要按规范看指定偏移。

魔数只是签名,不是校验:它只说明"像是这个格式",不保证完整,可以只贴个头来伪造。

三种状态其实是同一个东西

图片(或任何文件)本质上就是一串字节,二进制、十六进制、base64 只是同一串字节的三种写法:

PNG 文件头
  hex     89 50 4E 47
  base64  iVBORw0KGgo
  二进制  1000 1001 0101 0000 ...

所以看到 base64 以 iVBOR 开头,就能断定:解码后是 PNG 图片,只是还没落盘成文件。

一句话:图片是"内容",二进制 / base64 是"运输形式"。只要字节流符合文件头 + 结构,它就是图片。

为什么不用记"三种状态"

三种状态是同一个字节串的不同写法,会了 hex ↔ base64 ↔ 二进制互转,就能任意推导。实际只需要记住 hex 魔数,其余用工具转。

四、文件是怎么被读取的

读文件不是"看魔数符合就读",而是分两层:

第一层:决定"该交给哪个解码器"

系统/软件要先知道这是什么格式,依据优先级通常是:

  1. 扩展名(最常用):.png → 交给 PNG 解码器
  2. MIME 类型(浏览器/网络):image/png
  3. 魔数嗅探(拿不准时):读开头几个字节猜格式

魔数不是唯一入口,很多时候软件直接信扩展名;只有扩展名缺失/可疑时才靠魔数嗅探。file 命令、上传校验就是干这个的。

第二层:解码器按规范逐块解析

选定解码器后,它严格按该格式规范一步步走。以 PNG 为例:

1. 读前 8 字节签名 → 检查 = 89 50 4E 47 0D 0A 1A 0A
        不对 → 报错 "not a PNG"
2. 读 IHDR 块 → 拿宽、高、位深、颜色类型
3. 读 IDAT 块 → zlib 解压出像素数据(可能多个)
4. 读 IEND 块 → 结束
   每块还要校验长度和 CRC

音频同理:
- WAV:读 RIFF 头 → fmt 块拿采样率/声道 → data 块拿 PCM 数据
- MP3:没有固定头,靠逐帧同步(找 FF FB 等帧头)或开头 ID3 标签
- FLAC:检查 fLaC → 读 STREAMINFO 元数据块 → 帧数据

是"符合就读、否则报错"吗?

大致对,但要注意三点:

  1. 魔数只是入场券,不是充分条件;后面每块坏了照样可能报错。
  2. 解码器分严格/宽容两种:
    - 宽容(多数看图软件/浏览器):不认识的块跳过,尾部多余数据忽略
    - 严格(专业工具/校验脚本):CRC 不对、有多余数据都可能报错
  3. 报错表现不同:硬报错 / 部分渲染(花屏不报错) / 静默忽略。
拿到文件
   ↓
选解码器(扩展名 / MIME / 魔数嗅探)
   ↓
解码器按规范解析:
   ① 查魔数/签名 ── 不对 → 报错
   ② 逐块读结构 ── 坏块 → 报错 or 跳过
   ③ 校验(CRC/长度) ── 失败 → 报错 or 宽容忽略
   ↓
输出像素 / 音频样本
   (结束标记之后的数据 = 没人读,可藏文件)

关键结论:解码器是格式专属的。PNG 解码器只走 PNG 规则,MP4 解码器只走 MP4 规则——运行时没有"该用哪套规则"的犹豫,格式在第一步就定死了。

五、长度标志 vs 结束标志

不是所有文件都有"签名 + 结构 + 校验 + 结束标志"这四样,它们是常见套路而非统一法则。其中"怎么标记结束"有两种设计思路,选一个就够:

思路 做法 例子
长度前缀 段开头写"我有多长",读完就结束 MP4 的 box、PNG 的块内
结束标志 末尾放特殊字节表示"到此为止" JPEG FF D9、PNG IEND、GIF 3B

各格式实际用的方式

文件 签名 结构 校验 结束方式
PNG 有 分块 有 CRC 块内用长度,IEND 收尾(两者都用)
JPEG 有 分段 无 FF D9
GIF 有 分块 无 3B
ZIP 有 目录+条目 有 CRC32 EOCD(在文件末尾)
MP4 有(偏移4) box 无 无标记,读到字节用尽
ELF 有 段/节表 无 无
纯文本 无 极简 无 无,靠 OS 的 EOF

两种整体结束方式对比

段内定位 整体结束
PNG 每块长度 IEND 块
MP4 每 box 大小 字节读尽(无标记)

冷知识:同一格式可能两种都用。PNG 每块用长度字段,整体用 IEND;MP4 只有长度,没有结束块(大小字段为 0 表示"一直到文件尾")。

六、合并文件 / 藏文件的处理

合并分两种情况:尾部追加(A 后面接 B)和头部前置(B 前面塞 A)。核心还是一句:每个解析器只读自己的部分,读到自己的结束点就停,后面数据"看不见"。

尾部追加:A 解析器读到 A 结束就停

A.jpg + B.zip 拼一起,用图片软件打开:

JPEG 解码器:
  读 FFD8 → 解析各段 → 读到 FF D9(结束标志) → 停!
  FF D9 之后的所有字节(B.zip) → 完全不读,当不存在
  • PNG 读到 IEND 停;GIF 读到 3B 停
  • MP4 读到字节用尽,后面的 B 会被当"下一个 box",可能报错也可能被跳过

所以图片软件照样能正常显示 A,根本不知道后面还有 B。这就是"图片里藏压缩包"最常见的做法。

头部前置:B 前面塞 A(更麻烦)

用 B 的解析器打开:

  • 多数解析器从第 0 字节读签名,前面有垃圾 → 签名对不上 → 报错
  • 有些解析器会向后扫描找自己的签名,就能跳过前面的 A

ZIP 是最典型的特例(重要): ZIP 的总目录 EOCD 在文件末尾,解压工具从尾部往回找 50 4B 05 06:

操作 对 ZIP 的影响
zip 后面追加数据 EOCD 不在真正末尾 → 可能解不开(一般只在末尾 64KB 内找)
zip 前面前置数据 EOCD 还在末尾,工具找到它再用偏移定位 → 常照样能解

同类型合并

格式 拼接后行为
JPEG 多数只显示第一张(读到第一个 FFD9 停)
MP3 / MPEG 通常依次播放,天然支持流式拼接
GIF 可能只显示第一帧动画
TAR 设计上支持连读,靠两个全零块当结束标志
MPEG-TS 天然是连续流,拼接无感

Polyglot(一文件多格式)

一个文件同时是合法 A 又是合法 B(如 GIFAR:GIF + ZIP/JAR):
- 用图片软件打开 → 走 A 解码器
- 用解压工具打开 → 走 B 解码器
- 谁打开就用谁的规则,各读各的,互不干扰

怎么提取

解析器"看不见"后面数据,但提取工具是主动去找的:

binwalk -e 合并文件      # 扫全文件所有签名,逐个提取
foremost -i 合并文件     # 按类型恢复

手动提取要把解析器指向正确偏移:

d = open('merged.bin','rb').read()
i = d.find(b'PK\x03\x04')        # 找 B 的签名偏移
open('B.zip','wb').write(d[i:])  # 从该偏移切出来

扫描文件里所有已知魔数偏移:

sigs = {b'\x89PNG':'png', b'\xff\xd8\xff':'jpg', b'PK\x03\x04':'zip',
        b'GIF8':'gif', b'%PDF':'pdf', b'Rar!':'rar'}
d = open('suspect.bin','rb').read()
for s, name in sigs.items():
    i = d.find(s)
    while i != -1:
        print(f'{name} @ {i} (0x{i:x})')
        i = d.find(s, i+1)

其他藏法(结构冗余 / 隐写)

  • 结构冗余:PNG 的 tEXt/zTXt 块、JPEG 的 EXIF 注释、ZIP 注释字段、PDF 附件——都是规范允许的"合法藏法",exiftool 可看
  • LSB 隐写:把信息编码进像素最低位,藏的是"数据"不是"文件"(PNG 用 zsteg)

七、拿到 base64 / 二进制后怎么判断

不用每次都转十六进制,分三层,越靠前越省事:

拿到 base64 / 二进制
   │
   ├─ 第一层:直接认前缀(3 秒)
   │     base64 看开头: iVBOR→PNG  /9j/→JPEG  UEsD→ZIP  R0lG→GIF
   │     二进制看开头: 1000 1001 0101 0000 → PNG
   │
   ├─ 第二层:转成 hex 看文件头(确认)
   │     不确定就解码成字节 → 查 hex 魔数(查上表)
   │
   └─ 第三层:按魔数 + 结构验证(最严谨)
         只开头对不够,还要检查结构(尺寸/CRC/数据块)
         有些题只贴了个魔数开头、后面全乱 → 是伪造的

实操建议

  1. 直接看前缀认魔数;
  2. 不确定就解码成字节,查文件头 + strings 看可疑字符串;
  3. 确认是图片就保存成文件,用图片查看器 / xxd 验证能否正常打开。

把文本转回文件(核心:解码成字节,用 wb 写盘)

# base64 → 文件
py -c "import base64;open('out.png','wb').write(base64.b64decode(open('data.txt').read()))"
# hex → 文件(bytes.fromhex 自动忽略空格换行)
py -c "open('out.bin','wb').write(bytes.fromhex('89 50 4E 47'))"
# 二进制字符串 → 文件
py -c "s='01001000 01101001'.replace(' ','');open('o.bin','wb').write(int(s,2).to_bytes(len(s)//8,'big'))"

坑:① 二进制文件必须用 'wb',用 'w' 会按文本编码处理弄坏;② 命令行约 8K 长度上限,内容长就存 txt 再读;③ 存完按魔数核对,别信原扩展名。

八、容易混淆的"签名"

"签名"一词在不同语境下指三个完全不同的东西:

名称 是什么 用途
魔数签名 文件开头的几个固定字节 快速识别格式
数字签名 用私钥对文件内容做的加密校验 防篡改、验证来源(exe 的 Authenticode)
哈希值 文件内容的指纹(MD5/SHA) 完整性校验、证据固定、秒传

三者不是一回事:魔数在文件开头且固定;数字签名和哈希都依赖文件全部内容,内容变一点就全变。

data URI 伪装题示例

data:image/png;base64,iVBORw0KGgo...

data:image/png;base64, 表示"下面这段 base64 解码后是一张 PNG",去掉前缀 base64 解码即得图。注意声明格式可能骗人,按魔数判。

十、要点总结

  1. 文件 = 数据 + 元数据,本质是磁盘上一段带名字的字节序列。
  2. 文件类型由魔数决定,扩展名只是标签;魔数来自格式规范,是人为主导的约定。
  3. 二进制 / hex / base64 是同一串字节的三种写法,记 hex 就够。
  4. 读文件两层:先选解码器(扩展名/MIME/魔数嗅探),再按规范逐块解析;解码器是格式专属的。
  5. 魔数只是入场券,结构/校验还要过;宽容解析器会忽略多余数据。
  6. 结束方式两种:长度前缀 或 结束标志,二选一;有的格式两者都用。
  7. 合并文件:A 的解析器读到 A 结束就停,后面看不见;ZIP 因 EOCD 在末尾而特殊。
  8. 提取靠扫签名 + 按偏移切片(binwalk -e / 手动 find)。
  9. "签名"三义:魔数签名、数字签名、哈希值,别混。
  10. 记不住冷门类型没关系,交给 file / 工具箱。
